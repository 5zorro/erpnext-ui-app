Architecture comparison — Option B: Shell HTML

Dimension Option A — Thin inject over Vanilla WC Option B — Shell HTML (ground-up)
What runs in the WC Live ERPNext Desk — Frappe renders the form Shell-owned HTML — we render everything
How assumptions apply Shell injects assume.js + assume.css via executeJavaScript; touches cur_frm Assumption engine runs in shell; fields rendered conditionally — no injection
DOM stability Frappe re-renders strip injected state. Applier must re-fire on every render. We own the DOM. No re-render strips our state.
Vanilla field parity Free — Frappe renders all fields; we only suppress/decorate them. Manual — must port each PI field to our HTML. New ERP fields require a code change.
Added pickers / affordances Injected as DOM siblings. Must survive Frappe re-renders or be re-injected. Native — composable with bill-map, erp-form-bridge, commit-gate, ref-check.
Maintenance over time Frappe DOM selectors and cur_frm API drift across versions. Stable contract: we change our HTML on our own terms, not when Frappe does.
Initial build cost Low — wire assume.js into the session; no form rebuild. Higher — author PI fields in our HTML, wire erp-form-bridge.
Recommendation Good for a quick functional demo (P1). Long-term maintenance cost grows with Frappe version drift. Preferred for production: stable, composable, matches our existing Bill/PO/IR architecture exactly.
